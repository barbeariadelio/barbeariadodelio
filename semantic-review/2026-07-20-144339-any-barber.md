# "Qualquer Barbeiro Disponível" — Any-Employee Slot Selection

The feature lets a client skip barber selection and book the first available slot across all eligible employees for a given service and date. A new public endpoint (`GET /appointments/slots-any`) aggregates per-employee availability and returns a deduplicated, time-ordered list of `{ time, employeeId, employeeName }` objects. On the frontend, a sentinel card sits at the top of the barber grid; once the user picks a time, the resolved employee is surfaced inline and written into the booking payload at submission.

The design reuses `getAvailableSlots` cleanly, the sentinel `_id: '__any__'` prevents the normal slots query from firing, and the resolved-employee reveal UX is well-executed. **Watch for:** the deduplication strategy consistently assigns every shared timeslot to the same employee (insertion-order bias), not a random or least-busy one; vacations and blocked-days are not pre-filtered before the fan-out, adding unnecessary DB round-trips; and the edit flow does not restore `anyBarber` state, leaving the barber step in an ambiguous visual state on re-edit.

---

## High-level view

The backend aggregates slots by calling `getAvailableSlots` in parallel for every eligible employee, then deduplication keeps the first employee whose slot appears by iteration order. Because MongoDB document ordering is deterministic (insertion order by default), the same employee will always get priority for every shared timeslot — effectively the feature books the "first-created employee" rather than any random available one. This may or may not be intentional, but it's a silent policy choice worth making explicit.

`getAvailableSlotsForAnyEmployee` does not pre-filter employees by vacation or blocked-day before dispatching parallel `getAvailableSlots` calls. Each inner call does the check and returns `[]`, so correctness is preserved — but the unnecessary fan-out scales with headcount and is a one-line fix.

On the frontend, `anyBarber` and `resolvedEmployee` state only live in the current session. The edit flow restores service, employee, date, and time from the server but never sets `anyBarber = true`. The confirm page display is actually correct (it falls through to `selectedEmployee?.name`, which is restored), but the barber-step card shows the real employee highlighted rather than the "Qualquer" card — a user re-editing sees a state that doesn't reflect how they originally booked.

The `/slots-any` endpoint is public (no auth), matching the existing `/slots` endpoint. Both return `[]` for bad input rather than a 4xx, which is consistent but makes a mistyped `serviceId` indistinguishable from "no availability" on the client side.

<summary>Issues (5)</summary>

1. **Non-random employee assignment** — Deduplication by iteration order means the same employee always wins every timeslot they share with others. If load balancing matters, shuffle `eligible` before `Promise.all`, or pick the employee with the fewest bookings that day. The current behavior is a silent policy decision. *(confirmed)*

2. **Capacity halved with identical schedules** — When employees A and B both have 10:00 free, only A's slot appears. A two-barber shop with identical schedules shows half the expected available capacity. This may be acceptable by design ("one slot per time, one barber assigned"), but it's not documented and would surprise a shop owner. *(confirmed)*

3. **Edit-mode barber card mismatch** — `editAppt` restoration sets `selectedEmployee` to the real employee but never sets `anyBarber = true`. The barber step will highlight the real employee card rather than the "Qualquer" card. A user returning to step 1 from an any-barber booking will think they originally chose that specific barber, which may cause an unintended re-selection. *(confirmed)*

4. **No pre-filter for vacation/blocked-day in fan-out** — `getAvailableSlotsForAnyEmployee` selects only `_id name serviceIds` from employees, so vacation and blocked-day data are unavailable before dispatch. Projecting `vacations blockedDays` and filtering before `Promise.all` avoids N unnecessary DB round-trips on days where employees are off. *(confirmed)*

5. **Silent `[]` for non-existent service** — The controller guard and the service's own check both return `[]` when `serviceId` doesn't exist or is inactive. This matches `/slots` behavior but means a mistyped `serviceId` looks identical to "no availability" to the caller. A 404 for a non-existent service would be more debuggable. *(confirmed)*

<details>
<summary>Details</summary>

### Deduplication strategy and load distribution

`getAvailableSlotsForAnyEmployee` fans out to all eligible employees via `Promise.all`, then iterates the results in array order and uses a `Map` keyed on `time` to keep only the first entry per timeslot. The array order comes from `UserModel.find`, which defaults to natural (insertion) order in MongoDB. There is no shuffle, no weighting by current-day booking count, and no round-robin.

On a two-barber shop with identical schedules, the first-inserted employee receives every "any barber" booking. The simplest fix is shuffling `eligible` before dispatch:

```ts
eligible.sort(() => Math.random() - 0.5); // before Promise.all
```

If "least busy first" is preferred, the parallel results already contain enough information — an employee with more empty slots has fewer bookings that day.

### Edit-mode barber step state

The pre-fill `useEffect` calls `setSelectedEmployee(emp)` but not `setAnyBarber(true)`. On the confirm step, the Barbeiro row renders correctly because the expression falls through to `selectedEmployee?.name`. The gap shows up when the user navigates back to the barber step: the real employee's card is highlighted, not the "Qualquer" card. From there, clicking "Qualquer" would reset `resolvedEmployee` to null and clear `selectedTime`, which forces re-selection of a slot — the user is silently pushed through an extra flow step for an edit that shouldn't require it.

The fix is to detect during restore whether the appointment was created via any-barber mode. Since the appointment model doesn't store that flag, the most pragmatic approach is: if `editAppt.source === 'guest'` and the `anyBarber` query param is present, or simply always restore `anyBarber = false` and let the edit proceed in specific-employee mode (which is unambiguous and correct for editing).

### Vacation / blocked-day pre-filter

```ts
const employees = await UserModel.find({
  unitId, role: 'employee', isActive: true, allowOnlineBooking: { $ne: false },
})
  .select('_id name serviceIds') // ← vacations and blockedDays not projected
  .lean();
```

Adding `vacations blockedDays` to the projection and filtering before `Promise.all`:

```ts
const eligible = employees.filter((emp: any) => {
  if (emp.blockedDays?.includes(date)) return false;
  if (emp.vacations?.some((v: any) => date >= v.start && date <= v.end)) return false;
  if (!emp.serviceIds || emp.serviceIds.length === 0) return true;
  return emp.serviceIds.map((id: any) => id.toString()).includes(serviceId);
});
```

This eliminates one `AppointmentModel.find` + schedule query per absent employee.
